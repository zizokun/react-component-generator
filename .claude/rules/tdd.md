# TDD Rules

> **경고: 이 규칙은 Rigid다. 상황에 맞게 변형하지 마라.** 해석의 여지가 있으면 더 엄격한 쪽을 따른다.

## 0. 우선순위

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 프로젝트 규칙이 없을 때 적용하는 **기본값(fallback)** 이다.
- 프로젝트 규칙이 일부만 다루면, 다루지 않은 부분에만 이 파일을 적용한다.

## 1. 적용 기준

### TDD 필수

- **비즈니스 로직** (도메인 규칙, 계산, 상태 전이)
- **API** (엔드포인트, 요청 검증, 응답·에러 매핑)
- **유틸리티 함수** (파서, 변환기, 포매터, 정규화 함수)
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성)

### TDD 불필요

- **타입 정의** (interface, type, enum 선언만 있는 파일)
- **설정 파일** (빌드, 린트, 번들러, CI, 환경 변수)
- **순수 UI** (로직 없이 마크업·스타일만 있는 컴포넌트)
- **SQL** (스키마, 마이그레이션, 쿼리 문자열)

판단이 애매하면 **TDD 필수로 분류**한다. UI 컴포넌트라도 조건 분기, 이벤트 처리, 상태 변화가 있으면 그 동작은 TDD 대상이다.

## 2. RED-GREEN-REFACTOR

### RED

- **하나의 동작 = 하나의 테스트.** 한 테스트에서 여러 동작을 검증하지 않는다.
- 테스트를 작성한 뒤 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 오타, 잘못된 테스트 설정으로 실패했다면 테스트를 고친 뒤 다시 실행한다.
- 처음부터 통과하는 테스트는 아무것도 검증하지 않는다. 테스트가 올바른 대상을 보고 있는지 다시 확인한다.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 지금 테스트가 요구하지 않는 분기, 옵션, 추상화, 예외 처리를 추가하지 않는다.
- **신규 테스트와 기존 테스트가 모두 통과**하는지 전체 테스트를 실행해 확인한다.
- 기존 테스트가 깨졌다면 다음 단계로 넘어가지 않고 GREEN 안에서 해결한다.

### REFACTOR

- 대상: **중복 제거, 이름 개선, 헬퍼 추출.** 테스트 코드도 리팩터링 대상이다.
- 변경할 때마다 테스트를 실행해 **green을 유지**한다.
- **새 동작 추가 금지.** 새 동작이 필요하면 REFACTOR를 끝내고 RED로 돌아간다.

### 반복

- 다음 동작을 하나 골라 **RED로 돌아간다.**
- 구현할 동작 목록이 빌 때까지 사이클을 반복한다.

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다면 **그 코드를 삭제하고 RED부터 다시 시작**한다.
- **"참고용"으로 남기는 것도 금지**한다. 주석 처리, 별도 파일, 다른 브랜치, 임시 보관 모두 포함한다.
- 삭제한 코드를 기억에 의존해 그대로 다시 쓰지 않는다. 테스트가 요구하는 만큼만 새로 작성한다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순하면 테스트도 1분이면 쓴다. 단순한 코드일수록 경계값에서 깨진다. **예외 없음.** |
| "나중에 추가하겠다" | 나중은 오지 않는다. 구현 후 쓴 테스트는 실패를 본 적이 없어 검증력이 없다. **지금 RED부터.** |
| "시간이 없다" | 테스트 없이 아낀 시간은 디버깅과 회귀 대응으로 더 크게 돌아온다. 시간이 없을수록 **범위를 줄이고 TDD는 유지**한다. |
| "삭제하면 낭비" | 이미 쓴 코드는 매몰 비용이다. 남겨두면 테스트가 코드를 따라가게 된다. **삭제하고 다시 쓴다.** |
| "프로토타입이다" | 프로토타입은 거의 항상 프로덕션이 된다. 정말 버릴 코드라면 버릴 브랜치에서 쓰고, 남길 코드는 **TDD로 다시 작성**한다. |
