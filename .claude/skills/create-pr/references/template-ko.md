# PR 본문 템플릿 (국문)

저장소에 자체 PR 템플릿이 없을 때만 사용한다. 섹션 제목은 그대로 두고, 내용이 없는 선택 섹션은 통째로 지운다. 빈 섹션이나 "없음"을 남기지 않는다. 템플릿의 HTML 주석은 작성 안내이므로 최종 본문에서 지운다.

## 템플릿

```markdown
## 요약

<!-- 이 PR이 무엇을 왜 바꾸는지 1~3문장. 리뷰어가 diff를 열기 전에 의도를 알 수 있게 쓴다. -->

## 변경 사항

<!-- 사용자·동작 관점의 변화를 항목으로. 파일 목록이 아니라 무엇이 달라졌는지를 쓴다. -->
-

## 검증

<!-- 실제로 실행한 명령과 결과만. 수동 확인은 무엇을 어떻게 확인했는지. -->
- `<명령>` — <결과>

## 리뷰 포인트 (선택)

<!-- 리뷰어가 특히 봐야 할 곳: 설계 판단, 트레이드오프, 확신이 낮은 부분, 의도적으로 하지 않은 것. -->
-

## 관련 이슈 (선택)

<!-- 커밋 메시지나 브랜치명에 이슈 번호가 있을 때만. 닫는 이슈는 Closes #번호. -->
```

## 작성 지침

- **요약**: 무엇을 추가했는지보다 그 결과 무엇이 달라지는지를 쓴다. 커밋 메시지를 이어 붙이지 않는다.
- **변경 사항**: 커밋이 여러 개면 커밋 단위가 아니라 의미 단위로 묶는다. 동작 변화 없는 리팩터링은 따로 한 줄로 적는다.
- **검증**: 실패한 검증도 숨기지 않는다. 테스트를 추가했다면 무엇을 검증하는 테스트인지 한 줄로 쓴다.
- **리뷰 포인트**: 남은 한계나 후속 작업이 있으면 여기에 적는다. 리뷰어가 같은 질문을 반복하지 않게 하는 것이 목적이다.

## 예시

```markdown
## 요약

프롬프트가 500자를 넘으면 입력창에서 바로 에러를 보여주고 생성 요청을 막는다.

## 변경 사항

- 앞뒤 공백을 제외하고 코드 포인트 단위로 길이를 세는 `validatePrompt` 유틸 추가
- 500자 초과 시 에러 메시지 표시, 생성 버튼과 Cmd+Enter 제출 모두 차단

## 검증

- `bun run test` — 22개 통과 (유틸 4개, PromptInput 4개 추가)
- `bun run lint`, `bunx tsc -b` — 통과

## 리뷰 포인트

- 길이 제한은 클라이언트에만 있다. `/api/generate`를 직접 호출하면 우회되며, 서버 검증은 후속 작업으로 남긴다.
```
