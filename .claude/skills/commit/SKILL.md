# Commit

변경사항을 읽고 커밋 계획을 세운 뒤, 사용자 승인을 받고 커밋한다. 승인 전에는 스테이징도 커밋도 하지 않는다.

## Step 1. 변경사항 수집

아래 명령을 병렬로 실행한다.

```bash
git status --short
git diff                 # 스테이징 안 된 변경
git diff --staged        # 이미 스테이징된 변경
git log --oneline -10    # 기존 메시지 스타일 확인
```

- 추적되지 않은 파일(`??`)은 내용을 직접 읽어 무엇인지 파악한다. 디렉터리면 `git status --short -uall <dir>`로 펼친다.
- 변경이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.
- 이미 스테이징된 파일이 있으면 사용자가 의도한 묶음일 수 있다. 계획에 그 사실을 표시하고, 다른 단위와 섞지 않는다.
- 사용자가 인자로 범위를 지정했으면(예: "스타일만", "src/components") 그 범위만 다룬다.

## Step 2. 커밋에서 제외할 파일 확인

다음은 계획에 넣지 않고, 발견하면 사용자에게 따로 알린다.

- 비밀값: `.env`, `.env.*`(단 `.env.example` 제외), `*.pem`, `*.key`, 자격 증명이 들어 있는 설정 파일
- 생성물·캐시: `node_modules/`, `dist/`, `build/`, `coverage/`, `.DS_Store`, 로그 파일
- 디버그 흔적: 임시 확인용 파일, 주석 처리된 대량 코드, 남겨진 `console.log`

`.gitignore`에 있어야 할 파일이 추적되고 있으면 `.gitignore` 추가를 별도 `chore` 커밋으로 제안한다.

## Step 3. 논리적 단위로 분류

하나의 커밋은 "되돌릴 때 함께 되돌려야 하는 변경"의 묶음이다.

- 기능 추가와 그 기능의 테스트, 스타일, 타입은 한 커밋으로 묶는다.
- 서로 독립적인 기능·버그 수정은 나눈다.
- 동작 변화 없는 리팩터링과 포맷팅은 기능 변경과 분리한다.
- 의존성(`package.json`, lock 파일)은 그것을 쓰는 코드와 함께 묶는다. 단순 버전 업데이트면 `chore`로 분리한다.
- 분할 단위는 파일이다. 한 파일에 성격이 다른 변경이 섞여 있으면 억지로 쪼개지 말고(`git add -p`는 이 환경에서 쓸 수 없다) 더 큰 쪽 커밋에 포함하고, 계획에 그 사실을 적는다.
- 변경이 작고 한 가지 목적이면 커밋 하나로 충분하다. 쪼개는 것 자체가 목표가 아니다.

순서는 의존 관계를 따른다. 다른 커밋이 쓰는 코드(공용 컴포넌트, 타입, 설정)를 먼저 커밋해서, 각 커밋 시점에 빌드가 깨지지 않게 한다.

## Step 4. 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택)>
```

| type | 쓰는 경우 |
|---|---|
| `feat` | 사용자가 체감하는 기능·UI 추가 또는 변경 |
| `fix` | 버그 수정 |
| `refactor` | 동작은 그대로 두고 코드 구조 개선 |
| `chore` | 빌드, 설정, 의존성, 문서, 테스트 보강 등 그 외 |

요약 작성 규칙:

- 한국어, 50자 이내, 마침표 없음
- 무엇을 바꿨는지를 결과 중심으로 쓴다. "수정", "변경"만으로 끝나는 모호한 요약은 쓰지 않는다.
  - 좋음: `feat: 생성된 컴포넌트 미리보기 영역 확대`
  - 나쁨: `feat: CSS 수정`
- 파일 이름 나열이 아니라 의도를 적는다.

본문은 이유나 맥락이 diff만으로 드러나지 않을 때만 쓴다. 한 줄 72자 안팎으로 끊고, `- `로 시작하는 짧은 항목으로 적는다.

저장소의 기존 커밋이 다른 컨벤션(예: scope 포함 `feat(ui):`)을 일관되게 쓰고 있으면 그 형식을 따르고, 계획에 그렇게 했다고 적는다.

## Step 5. 계획 제시와 승인

커밋 전에 계획을 아래 형식으로 보여준다.

```
커밋 계획 (2개)

1. feat: 레트로 플래티넘 테마로 전체 화면 개편
   - src/App.tsx
   - src/App.css
   - src/components/Window.tsx (신규)

2. chore: 커밋 스킬 추가
   - .claude/skills/commit/SKILL.md (신규)

제외: .env (비밀값), .DS_Store
```

그런 다음 AskUserQuestion으로 승인을 받는다. 선택지는 "이대로 커밋", "메시지 수정", "단위 다시 나누기"로 둔다.

- 사용자가 수정을 요청하면 계획을 고쳐 다시 보여주고 다시 승인받는다.
- 승인 없이는 Step 6으로 넘어가지 않는다. 사용자가 이번 요청에서 "확인 없이 바로 커밋해"라고 명시한 경우에만 승인 단계를 건너뛴다.

## Step 6. 커밋 실행

계획 순서대로 커밋마다 다음을 한다.

```bash
git add -- <파일 경로들>          # 계획에 있는 파일만, 경로를 명시
git diff --staged --stat          # 의도한 파일만 올라갔는지 확인
git commit -m "$(cat <<'EOF'
<type>: <요약>

<본문>
EOF
)"
```

- `git add -A`, `git add .`은 쓰지 않는다. 계획에 없는 파일이 섞이는 것을 막기 위해서다.
- 삭제된 파일도 `git add -- <경로>`로 스테이징한다.
- 하네스가 지정한 커밋 attribution 줄(예: `Co-Authored-By`)이 있으면 메시지 끝에 붙인다.
- `--no-verify`, `--amend`, `git push`는 사용자가 명시적으로 요청하지 않는 한 쓰지 않는다.
- pre-commit 훅이 실패하면 출력을 보여주고 원인을 고친 뒤 **새 커밋으로** 다시 시도한다. 고칠 수 없으면 멈추고 사용자에게 알린다.

## Step 7. 결과 보고

모든 커밋이 끝나면 `git log --oneline -<커밋 수>`와 `git status --short`를 실행해 결과를 보여준다.

- 만든 커밋의 해시와 메시지
- 커밋하지 않고 남겨둔 파일과 그 이유
- 실패한 단계가 있으면 어디서 멈췄는지

push는 하지 않았다는 점을 한 줄로 알린다.
